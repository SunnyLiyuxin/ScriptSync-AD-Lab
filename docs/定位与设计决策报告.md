# ScriptSync 定位与设计决策报告

> 本报告基于「ScriptSync 应该解决什么痛点」的深度思考，给出平台定位、功能取舍、交互设计与迭代计划。所有决策以「推动口述影像准备环节效率」为唯一标准。

---

## 一、平台定位结论

**一句话定位**：ScriptSync 是「口述影像准备环节的协作中枢」，不是网页版 Aegisub。

### 判断依据

- Aegisub 在「单机编辑精度」领域已打磨十几年（帧级波形、频谱图、样式管理器、karaoke、本地 GPU 渲染）。用浏览器 + Canvas 永远追不上它的精度上限，追上也没有意义——因为它解决的是「一个人怎么把字幕打磨到帧精确」。
- 口述影像准备环节的真实效率黑洞不在这里，而在**协作层**：写稿人各自用 Aegisub 写完初稿 → 微信传文件 → 统筹人手动合并 → 截图批注 → 再传回 → 再合并 → 线下约时间演练 → 发现问题再改。这个流程散落在 5 个工具里，没有统一中枢。
- ScriptSync 的护城河是 Aegisub 架构上做不到的事：**多人实时协同 + AI 行业规范检测 + 批注审阅闭环 + 演练模式 + 云端版本**。这些都需要服务端 + 实时通信 + 用户系统，单机软件天然无法实现。

### 红海陷阱 vs 护城河路径

- **红海陷阱**：如果把精力花在「做网页版 Aegisub」（追帧级波形、样式编辑器、频谱图），就会陷入「用更弱的工具打它最强的领域」，永远落后。
- **护城河路径**：编辑器「够用就行」（秒级精度 + 轻量波形 + 表格行式），把精力压在协作工作流和 AI 上。

## 二、Aegisub 互补边界

| 能力 | Aegisub | ScriptSync | 取舍理由 |
|---|---|---|---|
| 帧级波形缩放 | ✅ 十年打磨 | ❌ 不做 | 浏览器 Canvas 追不上，且口述影像不需要帧精确 |
| 频谱图 | ✅ | ❌ 不做 | 同上 |
| ASS 样式编辑器 | ✅ 完整 | ❌ 不做 | 口述影像样式固定，不需要可视化样式编辑 |
| Karaoke 逐字时间 | ✅ | ❌ 不做 | 口述影像不需要 |
| 单机性能 | ✅ 零延迟 | ❌ 不竞争 | 浏览器有固有开销 |
| **多人实时协同** | ❌ 单机架构 | ✅ Yjs CRDT | 架构上做不到，是核心护城河 |
| **AI 客观中性检测** | ❌ 无服务端 | ✅ 百炼 | 行业规范刚需 |
| **用词一致性检测** | ❌ | ✅ | 多人写稿术语统一痛点 |
| **批注审阅工作流** | ❌ | ✅ 内联批注+状态机 | 闭环协同 |
| **工作分配+权限** | ❌ | ✅ | 防误改+分工 |
| **演练模式** | ❌ | ✅ 语音房间+提词器 | 写完即演练闭环 |
| **版本快照** | 仅文件级 | ✅ 文档级 | 随时回滚 |
| **云端存储+多端** | ❌ | ✅ | 不丢文件 |

### ASS 互导工作流（关键设计）

```
Aegisub 写初稿（个人精度打磨）
    ↓ 导出 ASS
ScriptSync 导入（协作中枢）
    ↓ 多人协同 + AI 检测 + 批注 + 演练
    ↓ 导出 ASS
Aegisub 精修（必要时，帧级对齐）
    ↓ 导出 ASS
ScriptSync 再导入（继续协作审阅）
    ↓ 定稿导出
```

这个循环成立，无断裂点——ASS 是开放文本格式，导入导出无损。ScriptSync 与 Aegisub 是**互补关系**而非竞争关系：ScriptSync 管协作工作流，Aegisub 管精度打磨，各司其职。

## 四、视频-编辑器同步范式选型

### 推荐：范式 C（混合式）

| 范式 | 描述 | 推荐? | 理由 |
|---|---|---|---|
| A（Aegisub 式） | 左侧视频+帧级音轨，拖动游标→右侧高亮 | ❌ 放弃 | 与 Aegisub 同质化，波形精度追不上，且偏离协作中枢定位 |
| B（纯表格） | 左侧视频独立，右侧表格为主，无波形 | ❌ 放弃 | 丢失「定位辅助」能力，空白段找不到，效率下降 |
| **C（混合式）** | **轻量波形作定位辅助（点击跳转+静音段标记），表格为主编辑面，视频为辅** | ✅ **推荐** | 既保留定位效率，又不与 Aegisub 竞争精度 |

### 当前实现评估

当前已是范式 C，但有以下缺陷需补全：

1. **当前行高亮跟随**：视频播放时，右侧表格中 `start ≤ currentTime ≤ end` 的行应自动高亮 + 自动滚动到可视区。**当前只高亮不滚动**，需补全自动滚动。
2. **波形点击跳转**：已实现（dispatch seek → onSeek → videoPlayer.seekTo）。
3. **行点击跳转视频**：已实现（selectRow → onSeek）。

### 波形实现难度

当前 FFmpeg 服务端提取（8000 peaks + silencedetect）已足够，无需升级到浏览器 Web Audio。精度上限是秒级，对口述影像够用。

**行动**：补全「视频播放时表格当前行自动滚动到可视区」。

## 五、用户系统方案

### 注册方式

**MVP 推荐：邮箱 + 密码注册**（不接短信验证码）

- 理由：短信验证码需要短信服务商（阿里云短信/腾讯云短信），有成本和审核门槛，MVP 阶段不必要。邮箱注册零成本、无审核、足够验证身份。
- 手机号短信验证码列为 V2 可选。

### 密码存储

- bcrypt 哈希（cost factor=12），禁止明文。
- 后端 FastAPI 用 `passlib[bcrypt]`。

### 个人信息最小化

- 仅收集：邮箱 + 昵称。不收集真实姓名、身份证、手机号。
- 合规要点：注册时勾选隐私协议，明示不收集敏感信息。

### JWT 鉴权

- access token：有效期 2 小时（短，防泄露）。
- refresh token：有效期 7 天（长，免频繁登录）。
- 刷新流程：access 过期 → 前端用 refresh 调 `/api/auth/refresh` → 拿新 access。
- 当前是单 token（永不过期的 dev token），需升级为双 token。

### 第三方登录

**MVP 不接入 OAuth**，邮箱注册已足够。V2 可接 GitHub OAuth（开发者友好）。

**行动**：
1. 后端新增 `users` 表 + `/api/auth/register` + `/api/auth/login` + `/api/auth/refresh` + `/api/auth/me`。
2. 前端新增注册/登录页 + 路由守卫 + token 刷新拦截器。
3. 密码 bcrypt，JWT 双 token。

## 六、邀请码流程

### 推荐：邀请码 + 审批（无密码层）

理由：腾讯会议的密码层是为了「立即进入」。ScriptSync 的邀请码是「申请加入 → 发起人审批」，已有审批这道人工关卡，再加密码层是冗余。除非未来要做「公开项目」（任何人凭码直接进），才需要密码层。

### 流程

```
1. 发起人创建项目
   → 系统生成邀请码（6位字母数字，如 X7K2P9）
   → 邀请码有效期 30 天，无使用次数限制

2. 用户在首页输入邀请码
   → 弹出项目预览卡（项目名 / 发起人 / 成员数 / 简介）
   → 点击「申请加入」

3. 发起人收到申请通知（顶部红点 + 通知列表）
   → 审批通过 / 拒绝
   → 通过后用户自动加入项目，角色=narrator

4. 用户加入后
   → 项目出现在「我的项目」列表
   → 进入项目即开始协同
```

### 邀请码生成规则

- 6 位大写字母+数字。
- 排除易混淆字符（0/O, 1/I/L）。
- 有效期 30 天，无使用次数限制。

**行动**：
1. 后端 `invitations` 表 + `/api/projects/{id}/invite-code`（生成）+ `/api/invitations/preview`（预览）+ `/api/invitations/apply`（申请）+ `/api/invitations/{id}/approve`（审批）。
2. 前端首页加「输入邀请码」入口 + 申请弹窗 + 发起人通知中心。

## 七、工作分配交互方案

### 推荐：双轨制（平台内分配 + 线下分工承接）

#### 方案 A：平台内分配（发起人在时间轴框选分配）

- 发起人进入「工作分配」模式 → 在波形/时间轴上拖选区间 → 弹出成员列表 → 指派。
- 自动创建 AssEvent（status=empty, assignedTo=该成员）。
- **难度评估**：中等。需要在波形上加拖选交互 + 成员选择弹窗。当前波形已有点击/双击交互，加拖选不复杂。

#### 方案 B：线下分工承接（批量导入 + 自动归属）

- 成员各自用 Aegisub 写完片段 → 导出 ASS。
- 发起人导入 ASS 时，根据 ASS 的 Style 或 Layer 字段自动识别归属人（如 Style 名含 `@张三` → 自动指派）。
- 或导入后手动批量指派（多选行 → 指定负责人）。
- **难度评估**：低。已有 ASS 导入，加归属识别规则即可。

#### 推荐路径

**两个都做**。方案 B 是主路径（承接 Aegisub 工作流），方案 A 是补充（平台内直接分工）。

### 视图模式

当前有「看所有 / 只看自己 / 按范围」三种。建议**补全第四种：按负责人筛选**（下拉选某成员，只看其负责的行）。

**行动**：
1. 波形加拖选区间交互 + 成员指派弹窗（方案 A）。
2. ASS 导入时解析 Style/Layer 自动归属 + 手动批量指派（方案 B）。
3. 视图模式加「按负责人筛选」下拉。

## 九、角色与权限矩阵

| 角色 | 说明 |
|---|---|
| owner | 发起人/统筹，项目创建者 |
| reviewer | 审阅人，可批注可编辑 |
| narrator | 写稿人，默认角色 |

### 权限矩阵

| 权限 | owner | reviewer | narrator |
|---|---|---|---|
| 分配工作 | ✅ | ❌ | ❌ |
| 审批加入 | ✅ | ❌ | ❌ |
| 批注他人行 | ✅ | ✅ | ✅ |
| 编辑自己负责的行 | ✅ | ✅ | ✅ |
| 编辑他人负责的行 | ✅ | ✅ | ❌（只读） |

| 版本管理 | ✅ | ❌ | ❌ |
| 查看所有行 | ✅ | ✅ | ✅ |

### 是否需要 guest（只读观察者）角色

**MVP 不做**。口述影像准备环节都是深度参与者，没有「只看不动」的场景。V2 若有培训/观摩需求再加。
