### 1\.1 口述影视是什么？我是谁 ？我们是谁 ？

#### · 口述员的工作，可以用一条音轨时间轴说清楚：

```Plain Text
电影原声： [  有台词  ] [  空白  ] [  有台词  ] [  空白  ]
口述员：   [ 客观补字幕 ] [ 描述画面 ] [ 客观补字幕 ] [ 描述画面 ]
```

简单说就是两件事：

1. 有台词时：口述员不抢话，客观讲述观众看不到的字幕信息，例如”她说：“ "他瞪大了眼睛说：”；

2. 没有台词的空白处：用语言描述场景画面、人物动作和神态。例如：”树叶摇曳，落日散发出蒙蒙光晕“

口述员的任务不止是“念字幕”或“报画面”。我们的核心是：**用生动、形象、又客观的语言，让视障者通过听觉在脑海中“看到”电影。**我们要做的是**把视觉信息翻译成听觉信息**，让声音成为他们的眼睛——不评价，不解释，把看得见的事实讲清楚，同时讲得有画面感、有节奏感，让人能“听”出一部电影来。

### 1\.2 我们看到了什么问题

### 目前现状：

目前口述影像的准备工作，说到底是靠人一寸一寸**“啃”**出来的。一部两小时左右的电影，口述员要么用最朴素的办法，打开 Excel，对着时间轴一行一行地填“几分几秒讲什么”；要么用 Aegisub 这类字幕软件，先让机器自动识别原片字幕，再在字幕轨上手动添加口述内容。几个人分段写完之后，稿子还要合在一起，由审核人员用肉眼逐条检查：*人称是不是统一了，前后段落接不接得上，有没有漏掉关键信息，语速和留白合不合适。*这件事非常耗时，而且人的注意力有限，尤其多人协作时，“你写这段、我写那段”造成的**衔接误差、用词不一致、称呼混**乱，光靠人眼很难全部发现。所以我们才需要把** AI 引入写稿、审核环节**——不是替代口述员去创作，而是让它在合稿之后快速扫一遍，帮人把那些低级的、重复的、容易被忽略的问题先挑出来，**让人把精力留给真正需要感受和判断的部分**。

我深刻体会到：**不是没有好电影，也不是没有愿意讲的人，而是筹备一部电影太慢、太累、太依赖少数人的线下协作。**一场两小时的电影，往往需要聚集五到六位口述员，每人分到二十\~三十分钟左右的片段。

目前我们是这样做的：

- **写稿：**用 Aegisub 逐行写稿

- **合稿：**通过"述格"网站（王孟琦老师制作的网站：[sg\.kadaiad\.fun:4680](http://sg.kadaiad.fun:4680)）把每个人导出的 ASS 转换成 Excel，再在共享表格里拼合

- **对齐：**反复线下对齐、排练

**从写稿到真正放映，至少一个月。这导致活动频次上不去，每月能办一场已是常态。**

### 1\.3 我们为什么不直接用 AI 语音

目前一些大厂和机构已经在 AI 生成口述语音上做了很多探索，技术层面已能做到相当自然流畅的解说。但实际应用到真实场景中，普及度仍然不高：

大部分口述工作，尤其是线下有组织的观影活动，仍然依靠口述员以传统手艺来完成。AI 方案更多适用于视障朋友自己在家点播、小规模使用的场景；而当我们想要组织一场线下集体观影时，就需要口述员专门到场完成讲述——因为现场有互动、有氛围、有情感传递，这些是 AI 难以完全替代的。

**我们不想取代口述员，我们想在保留"人来讲"的前提下，把准备环节的效率提上去。**

### 1\.4 我们做了什么

因此，作为团队的一名探索AI的”初学者“，我希望做一个**垂直到极致**的协作平台——ScriptSync。它不追求大而全，只解决口述稿准备中最实际的几个问题，把口述影像准备阶段的 9 个散落步骤（立项→片源→分析→分配→撰写→审阅→定稿→导出→演练）收进一个系统，每一步的输出自动成为下一步的输入。

**一句话定位：ScriptSync 是"口述影像准备环节的协作中枢"，不是网页版 Aegisub。我们与 Aegisub 互补而非竞争——编辑器"够用就行"，核心护城河是 Aegisub 架构上做不到的事：多人实时协同 \+ AI 行业规范检测 \+ 批注审阅闭环 \+ 演练模式 \+ 云端版本。**

## 二、核心功能

### 2\.1 实时多人协作

基于 Yjs CRDT 算法实现无冲突多人实时协同编辑，告别"一个人导出 Excel、另一个人粘贴合并"的传统流程。

- **文档同步：**多人同时写稿，所有编辑实时同步，无冲突自动合并

- **在线感知：**awareness 协议实时显示在线用户头像与昵称，成员加入/退出即时反映

- **冲突解决：**基于 Y\.Array/Y\.Map 原子事务，并发编辑不会互相覆盖

- **离线缓存：**y\-indexeddb 本地缓存，断网期间编辑暂存，重连自动追平

### 2\.2 按时间范围导入与自动归位

每个人的片段自动插入到正确位置，不再手动排序。

- **有序插入：**导入 ASS 字幕时按时间有序插入，多人导入后视图自然合并

- **内容归属：**记录导入者 userId 作为 owner 字段，支持"只看自己"过滤

- **全局排序：**按视频全局时间升序排列，保证多人导入后视图一致

### 2\.3 邀请码制项目准入

创建人邀请成员，成员加入后实时可见彼此在线状态。

- **邀请码生成：**创建人点击"邀请协作"，后端用 crypto 安全生成唯一随机邀请码（字母数字混合）

- **绑定校验：**邀请码与项目 ID 绑定，支持有效期、最大使用次数、角色分配

- **加入流程：**另一用户首页输入邀请码，后端验证有效后直接跳转至对应项目工作页面

- **历史记录：**加入后项目入口出现在用户首页项目列表，方便再次进入

### 2\.4 状态与权限管理

普通成员可标记"需修改"并显示头像，创建者可批量审核、锁定、删除。

**角色权限矩阵（4 种角色 × 8 种权限）：**

**字幕条目状态机（6 态流转）：**draft（初稿）→ needs\_revision（需修改）→ in\_review（审阅中）→ approved（已通过）→ locked（已锁定）；deleted（已删除，可由 owner 恢复）。

### 2\.5 内联批注审阅

像 Word 一样在字幕旁留下修改意见，所有批注实时同步。

- **批注气泡：**在任意字幕条目旁发起批注，支持嵌套回复

- **内联标记：**行前显示批注者头像，快速定位有讨论的条目

- **解决闭环：**批注可标记为"已解决"，与字幕状态联动

### 2\.6 AI 辅助检测

讲述电影的原则是：客观。所以，运用AI，提高对选中的行范围进行客观中性和用词一致性检查的效率，帮助减少低级错误。所有 AI 能力由阿里云百炼（dashscope）提供，精度优先。

- **客观中性改写：**qwen\-max 识别主观评价词，给出客观化改写建议，保留 ASS 内联标签

- **用词一致性：**qwen\-plus 检测全文术语不一致，支持一键批量替换

- **前后衔接检查：**qwen\-plus 检测相邻条目衔接问题（指代不明、主语缺失、语气不一致）

- **时长预估：**纯本地字符统计（3\.5 字/秒），检查文本时长是否匹配空白段

- **降级策略：**无 API key 时返回结构完整的空结果，不阻塞流程

##### 核心检测维度

1. 人称一致性：检测全文人物称谓、代词（他/她/它、该男子/女子等）是否统一，指出混用、前后不一致处。

2. 语气一致性：分析不同口述员负责的段落，识别语气、语体风格的突然变化，提示是否需统一。

3. 客观中性检测：识别文本中的主观评价词、情感色彩词、推断性表达（如“似乎”“好像”“大概”“很悲伤”“美丽的”），提示替换为可观察的动作、表情、场景描述。

4. 用词准确性与语法：检测错别字、语法错误、搭配不当、冗余表达，给出修改建议。

5. 衔接流畅度：评估相邻段落（特别是不同口述员交接处）的过渡是否自然，信息衔接是否连贯，有无重复、跳跃或逻辑断裂。

![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=NzcyOWVlNDVmMjRlMGQxNjc5MzczZDMzNDg0OTY4MmFfOTEwOGRlNDhkOWUwNWFlOTk5NDc4ZWY4MTg0Njg0ODVfSUQ6NzY3MzUzMDAwMzM2NzQ4MDI5NF8xNzg2Njc5NDIwOjE3ODY3NjU4MjBfVjM)

6. 时间适配度：根据每条口述的起止时间，估算文本长度与留白时长是否匹配，提示过密（可能压台词或语速过快）或过空（信息不足）。

7. 信息完整性：判断关键视觉信息是否遗漏，如场景转换、人物动作、重要道具、字幕信息等，给出补充建议。

8. 规范符合性：检查是否符合口述影像通用规范：不解释画面含义、不评价人物、不剧透后续、只描述当下可见内容。

##### 输出与交互

• 检测范围支持：当前勾选行集合、手动输入行号范围、手动输入时间范围。

• 检测结果以行内标记呈现：问题行显示对应颜色标记（如红色波浪线表示主观词，黄色下划线表示人称不一致等），悬停显示具体问题和建议。

• 提供汇总报告面板，按问题类型分组列出所有问题，点击可跳转到对应行。

• 所有检测结果仅供参考，不自动修改原稿，最终修改由口述员或审核人决定。

##### 技术实现要求

• 模型接入：使用阿里云百炼（Bailian）平台提供的模型API，优先选用通义千问系列模型（如 qwen\-max、qwen\-plus 或 qwen\-turbo），具体模型名称可在配置文件中指定。

• 鉴权方式：通过阿里云百炼API密钥（API Key）进行鉴权，密钥从环境变量中读取，不在前端暴露。后端需妥善存储密钥，可使用阿里云AccessKey或百炼专属API Key。

• 调用方式：后端通过HTTPS请求调用阿里云百炼的OpenAI兼容接口或原生DashScope接口，将口述稿分块送入模型，要求返回结构化JSON。

• 结构化输出：设计专门的prompt模板，要求模型返回JSON，包含：行号、问题类型、原文片段、建议修改、严重程度。可结合few\-shot示例提升稳定性。

• 上下文输入：模型输入需包含时间轴上下文（起止时间）和相邻行文本，以便判断时间适配和衔接问题。

• 异步执行与结果推送：检测任务异步执行，前端显示进度，完成后通过WebSocket推送结果。建议使用消息队列（如BullMQ）管理任务，避免阻塞主线程。

• 错误处理与重试：对API调用失败、超时等情况进行捕获，支持自动重试（最多3次），并记录日志。若模型返回格式不合法，需进行二次解析或降级处理。

## 三、产品亮点

### 3\.1 垂直到极致的业务理解

我们不是在做通用的协同文档，而是在做口述影像这个垂直领域的业务系统。每一个功能都对应口述员真实痛点：

- 过去用 Aegisub 写稿、用 Excel 合稿、用微信群对齐，现在全部收进一个工作台

- 保留"人来讲"的前提下提升效率，而非用 AI 替代人

- ASS 互导工作流：Aegisub 写初稿 → ScriptSync 协作 → 导出 ASS → Aegisub 精修，无损闭环

### 3\.2 真正的实时协作

基于 CRDT 算法实现的无冲突合并，区别于传统"加锁编辑"或"操作日志回放"方案：

- 多人同时编辑同一行，Yjs CRDT 自动合并，不会互相覆盖

- 二进制 diff 增量传输，带宽极低，弱网也能用

- 离线编辑暂存本地，重连自动追平，不丢数据

### 3\.3 AI 辅助而非替代

所有 AI 能力都围绕"帮口述员减少重复劳动"设计，而非试图替代口述员：

- 客观中性改写：识别主观评价词，但改写建议由人决定是否采纳

- 用词一致性：全文术语检查，一键替换，减少合稿后的低级错误

- 未来规划：衔接程度分析、流畅度检测、人情味保留度评估、语法错误检查

### 3\.4 完整的状态流转闭环

从初稿到锁定，6 态状态机覆盖完整生命周期，配合权限矩阵实现"谁该做什么"的清晰分工：

- 口述员只能编辑自己负责的行（数据层校验，非仅 UI 隐藏）

- 审阅者可标记"需修改"并显示头像，口述员一眼看到该改哪条

- 统筹可批量审核、锁定、删除，版本快照支持回滚

### 3\.5 零安装、即开即用

基于 Web 技术，浏览器打开即用，口述员无需安装任何软件，降低使用门槛。Docker 一键部署，便于团队私有化部署。

#### （二）、8 个检测维度的技术实现



##### 1\. 客观中性检测（`/api/ai/neutral-check`）

- \[narration\_review\.py\]\(file:///workspace/services/api/ai/narration\_review\.py\#L97\) `detect_subjective_rewrite()`

- 模型：`qwen-max`（单条文本）

- Prompt 约束口述影像行业规范，输出 `{original, subjective_spans:[{start,end,word}], rewritten, char_count}`

- 字符级 span 标注，前端按 `start/end` 高亮主观词，支持一键采纳改写

    

##### 2\. 用词一致性（`/api/ai/consistency`）

- 多事件批量入参 `events:[...]`，模型 `qwen-plus`

- 输出 `{word_a, word_b, occurrences:[{event_id, text}]}` 聚合同义词混用

    

##### 3\. 前后衔接（`/api/ai/continuity`）

- 跨事件对分析，输出 `{event_id_a, event_id_b, issue_type, description}`

- `issue_type` 枚举：衔接生硬 / 指代模糊 / 重复啰嗦 / 其他

    

##### 4\. 人称一致性（`/api/ai/person-consistency`）

- \[narration\_review\.py:454\]\(file:///workspace/services/api/ai/narration\_review\.py\#L454\) `check_person_consistency()`

- 检测称谓混用 / 代词不清 / 性别不一致，返回 `{event_id, issue_type, original, suggestion}`

    

##### 5\. 语气一致性（`/api/ai/tone-consistency`）

- 跨事件语气突变检测，按 `event_id_a/b` 配对标注

    

##### 6\. 语法准确性（`/api/ai/grammar`）

- 单条文本 `text`，模型 `qwen-plus`，输出 issues 数组

    

##### 7\. 信息完整性（`/api/ai/completeness`）

- 模型 `qwen-max`，输出带 `time_range` 的时间轴缺漏标注（如 "3\-6至6\-9之间"）

    

##### 8\. 规范符合性（`/api/ai/compliance`）

- 模型 `qwen-max`，输出 `{violation_type, severity, description}`，severity 分高/中/低

#### （五）、工程化设计要点



1. **统一契约**：8 个函数返回结构一致（`{issues:[...], model}` 或单条结构），前端用一套 `multiState` 模板渲染 6 个整段检测 tab

2. **错误隔离**：每个函数独立 try/except，单维度失败不阻塞其他维度

3. **成本控制**：模型分级（推理任务用 qwen\-max，审校任务用 qwen\-plus）\+ 前端并发限流 4

4. **可观测**：`logging` 记录每次调用失败与降级事件

5. **零破坏增量**：新增 5 函数 \+ 5 路由，未改动原有 6 个 AI 接口，向后兼容

    

核心就是：**FastAPI 异步路由 \+ DashScope SDK 结构化输出 \+ Svelte 5 响应式 \+ Yjs 协作文档**，把百炼大模型包装成 8 个垂直审校能力，通过 JWT 鉴权的 RESTful API 暴露给前端。

### 4\.6 安全与鉴权

- **JWT 双端共享：**Python API 与 Node\.js 协作服务端共享 JWT\_SECRET，HS256 签名

- **房间隔离：**协作服务端校验 payload\.projectId === roomName，防止越权访问其他项目

- **密码安全：**bcrypt（cost=12）哈希存储，禁止明文

- **权限校验：**数据层 canEdit 校验，即使绕过 UI 也拒绝越权写入

### 4\.7 部署方案

同一套代码，只改环境变量即可在本地与生产间切换：

- **本地开发：**docker\-compose 一键启动三端（frontend 5173 \+ collab 1234 \+ api 8000）

- **生产部署：**前端 Cloudflare Pages / 百炼静态托管；API 百炼 K8s；协作服务端 ECS

- **关键约束：**协作服务端和常驻 API 必须用 K8s（最小实例数≥1），不能用 Serverless（冷启动断连）

## 六、未来规划

未来，我们还会在这个平台上引入更细粒度的 AI 质量评估能力，专门针对多人合稿后的口述稿做：

1. **衔接程度分析：**检查不同口述员负责的段落之间过渡是否自然、语气是否连贯

这些技术不是为了替代人，而是为了帮口述员把更多精力放在"怎么讲得更好"上，而不是"哪里写错了、哪里接不上"。

它不是一个炫技的工具，而是一个让口述员少做重复劳动、多把时间花在打磨表达上的业务系统。

**我们承认，目前产品还在迭代中，很多功能刚刚跑通，还不够稳定。但方向是对的：我们不是用 AI 替代人，而是用 AI 和协同技术放大每一位口述员的能力，让更多视障朋友能够更频繁地走出房间，走进影院和图书馆，和所有人一样，享受正在发生的文化与社交生活。这才是这个产品存在的意义。**
